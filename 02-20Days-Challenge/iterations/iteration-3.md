# 迭代 03 · 升级把我自己的数据删了：34 项任务、登录态、四天日志

- **日期**：2026-11-13
- **对应版本**：1.4.1（事故版）→ 1.4.2 / 1.4.3（修复）
- **触发来源**：我自己装机时触发
- **本仓库提交**：`2b3fe76`（1.4.2：`desktop/Program.cs` **+296 行**、`installer/Setup.cs` **+203 行**）、`d9ccbb4`（1.4.3：`Setup.cs` **+198 行**，「升级保全日志与 cookie」）

---

## 一、现象

1.4.1 加了「安装前先卸载旧版」之后，我自己做一次覆盖安装，装完启动——**任务列表空了，学习通登录态没了，`process_logs/` 里的日志也没了。**

损失清单：
- 34 项任务
- 学习通登录态（cookie）
- 11-09 ~ 11-12 的运行日志（本机副本）

## 二、日志里的证据：一段 19 小时的空白

```json
{"local":"2026-11-12 22:53:02","app":"1.2.5","install":"d7776517-…","event":"app_stop","seq":4}
{"local":"2026-11-13 18:13:48","app":"1.3.9","install":"e6486fec-…","event":"app_start","seq":1}
```

- **11-12 22:53 之后，到 11-13 18:13 之前，一条记录都没有**——不是程序没跑，是日志文件被删了
- `install` 字段从 `d7776517…` 换成 `e6486fec…`——这是一次全新安装

**「没有日志」在这件事里就是最直接的证据。** 一个每天写几千条的程序，突然有 19 小时空白，只可能是文件本身没了。

## 三、根因：给旧版卸载器传了它不认识的参数

1. 1.4.1 的安装器会先调用旧版的 `Uninstall.exe`，并传 `/KEEPDIR` 想保住数据目录
2. **旧版卸载器根本没有这个参数**，它按老逻辑 `timeout 2 & rmdir /s /q` 删掉整个安装目录
3. 安装器这边只**固定等 2.5 秒**就开始解压新文件
4. 结果：删除动作在解压之后才真正执行，**刚解压的文件连同 `data\` 一起被清掉**

一句话：**我以为传个参数就能保住数据，但旧版不认识这个参数，而我又只等了 2.5 秒。**

## 四、改动

**A. 顺序改成可验证的**

```
备份 → 校验备份 → 卸载 → 轮询到目录确实消失 → 再等 2.5 秒 → 解压 → 恢复
```

关键是把"等固定时间"换成"**轮询到目录真的没了**"，固定等待只作为最后的缓冲。

**B. 备份要能证明是备份**

- 备份后校验**文件数 + 字节数**，不一致就**中止安装**，不硬装
- 备份滚动保留 2 份
- 恢复只补缺失文件，不覆盖已有

**C. 补 5 条契约测试**

其中两条直接以这次事故命名：
- `备份必须在卸载之前`
- `校验失败必须 throw`

## 五、验证

| 场景 | 结果 |
|---|---|
| 覆盖安装（有旧版 + 有数据） | 任务、登录态、日志全部保留 |
| 备份校验失败（人为改字节数） | 安装中止，旧版原样可用 |
| 连续升级两次 | 备份滚动保留 2 份，不无限堆积 |
| 全新安装 | 跳过备份，正常 |

## 六、复盘

**1. 唯一能救回来的原因，是我自己定的规矩。**
日志能恢复，是因为每天同步一份到作业仓库；任务能找回来，是因为数据在服务器上还有。**如果日志只存在本机，11-09~11-12 那四天就永久没了。**

**2. 破坏性操作不能依赖"对方的实现"。**
我给旧卸载器传 `/KEEPDIR`，是在假设"它会遵守"。**跨版本调用时，旧组件的行为只能当黑盒，必须自己验证结果**——轮询目录消失，就是不再相信对方的返回值。

**3. 固定等待是猜，不是同步。**
2.5 秒这个数字当初是拍脑袋的。**凡是"等一下应该就好了"，都要换成"等到某个条件成立"。**

**4. 这条 bug 是自己造的，也只有自己能修。**
用户不会触发得这么彻底——他们大多先卸载再装。**是我在测试"覆盖安装"这个新功能时把它撞出来的，也算自测的价值。**
