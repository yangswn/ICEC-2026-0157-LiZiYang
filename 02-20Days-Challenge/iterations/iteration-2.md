# 迭代 02 · 老用户装不上新版：`runtime\node.exe` 正由另一进程使用

- **日期**：2026-11-11 收到反馈 → 2026-11-13 修复发布
- **对应版本**：1.3.8 → 1.3.9
- **触发来源**：外部用户（小陈）从 1.2.4 升级到 1.3.x
- **本仓库提交**：`bb5051d`（同步源码至 1.3.9，`installer/Setup.cs` **+237 行**，11 个文件 265 增 20 删）、`b4c4bb4`（登记第 22 次迭代）
- **证据截图**：`feedback/14_xiaochen_upgrade_fail_chat_20261111.png`、`15_installer_file_in_use_20261111.png`、`16_node_process_taskmgr_20261111.png`

## 一、现象

小陈在旧版（1.2.4）基础上装新版，安装器弹窗报：

```
runtime\node.exe 正由另一进程使用，无法覆盖。
```

他自己打开任务管理器，结束了所有 Node 进程，**再点安装，还是同一个错**。

他的原话是：「关了后又出来了。」

## 二、日志里的旁证

升级之后程序能跑了，日志里能看到一次安装环境切换：

```json
{"ts":"2026-11-12T14:53:02.263Z","local":"2026-11-12 22:53:02","app":"1.2.5",
 "install":"d7776517-e7ec-4776-9a42-2eafaa629dae","event":"app_stop","seq":4}
{"ts":"2026-11-13T10:13:48.294Z","local":"2026-11-13 18:13:48","app":"1.3.9",
 "install":"e6486fec-e69f-4986-9405-39ac5b902588","event":"app_start","seq":1}
```

`install` 字段从 `d7776517…` 变成 `e6486fec…` —— **说明这是一次真正的重装，不是覆盖**。用户最后是靠"先卸载再装"绕过这个 bug 的，不是我修好的。

## 三、根因：三件事叠在一起

| # | 事实 | 后果 |
|---|---|---|
| 1 | 安装器覆盖文件前**不检查旧进程** | 文件被占用，装到一半失败 |
| 2 | 课铃常驻托盘，**点 × 只是隐藏**，主程序还在跑 | 用户以为关了，其实没关 |
| 3 | `node.exe` 由主程序托管，**杀掉会被立刻重启** | 用户在任务管理器里杀 node，永远杀不完 |

第 3 条是最容易误判的地方：**用户的操作没有错，是"杀进程"这个动作本身在这套架构下无效。**

## 四、改动（`Setup.cs` +237 行）

1. **装前检测**：扫描安装目录内的进程，列出「课铃正在运行（共 N 个进程）」
2. **按顺序关**：先主程序、后 `node.exe` —— **顺序反了会被主程序重新拉起**
3. **只按路径匹配**：额外要求 node 在 `runtime\` 子目录下，**不碰机器上其他 Node 程序**
4. **失败降级**：自动关不掉时给手动指引 + 重试按钮，**不静默失败**

## 五、验证

| 场景 | 结果 |
|---|---|
| 课铃正在运行（托盘）时升级 | 弹窗列出进程数，确认后自动关闭并完成安装 |
| 机器上有其他 Node 程序 | 不受影响（只匹配 `runtime\node.exe`） |
| 权限不足关不掉 | 给出"请手动结束 XXX"的指引 + 重试，不中断 |
| 全新安装（无旧版） | 跳过检测，直接装 |

## 六、复盘

**1. 用户报的是"装不上"，根因却是"关不掉"。**
如果只按字面去修"文件占用"，会写成重试三次然后放弃。**真正的解法是承认"这个进程在架构上就关不干净"，然后由安装器接手。**

**2. 前一条 bug 的修复制造了这条 bug。**
1.3.x 为了"点 × 不退出、保持提醒"，把主程序常驻了 —— 这正是文件被占用的原因。**功能修好了，副作用要一并想到。**

**3. 靠"先卸载再装"能绕过，说明失败的提示还不够。**
用户自己摸索出绕过方法，等于这一版安装器的价值只剩一半。**遇到"用户能自己绕过"的 bug，不能当成已解决。**
