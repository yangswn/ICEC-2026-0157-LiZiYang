## 二、本阶段：11-13 ~ 11-14（1.3.8 → 1.6.1，6 次迭代）

**一句话**：这两天不是在加功能，是在**修地基** —— 安装、启动、数据、状态判断，四个最容易塌的地方全撞了一遍。

### 2.1 两个触发点

- **小陈**（11-11 遇到，13 号才转达）：升级报「`runtime\node.exe` 正由另一进程使用」。他去任务管理器杀了 Node，**结果关了又自己回来**。
- **我自己**（11-13 晚）：装好 1.3.9 启动报 `E_ABORT (0x80040004)`，但日志显示 Node 服务已起、窗口也建好了。

### 2.2 六个版本

| 版本 | 起因 | 做了什么 | 结果 |
|---|---|---|---|
| **1.3.9** | 小陈 | 安装前按**可执行文件全路径**识别安装目录内的进程，弹窗后按「先主程序、后 node」关闭 | 装不上解决，且不误杀机器上别人的 node |
| **1.4.0** | 我自己 | 启动时抢命名互斥体 `Local\ClassBell.SingleInstance`，抢不到就提示并退出；启动错误翻译成人话 | 两个实例不再抢 WebView2 目录 |
| **1.4.1~1.4.3** | **我自己引入的事故** | 加「先卸旧版」后，旧卸载器的延迟删除把**刚装好的文件连同 `data\` 一起删了** | 本机 34 条任务、登录态、4 天日志全丢。日志靠作业仓库副本恢复，任务靠重新登录同步找回。修复：备份 → 校验 → 校验失败即中止安装 |
| **1.5.0** | 复盘 1.4.x | **推倒重来**：「先卸载再装」这个方向本身是错的，改成覆盖安装 | 代码净减约 100 行，中间不再有「软件没了」的空窗 |
| **1.6.0** | 我查自己的数据 | 以为 28 条作业缺截止时间，去详情页补 → **补到 0 条**（那 28 条全是已提交/已批改）。但发现**16 条已交作业被当成待办** | 待办 22 → 12，列表终于是真的 |
| **1.6.1** | 小臻第二次读源码 | 非法日期静默进位、空请求体崩溃、月度重复改日期后跳回 | 81 项测试，三条全修 |

### 2.3 三件值得单独讲的事

**① 我犯过一个真错（1.4.x）**
给旧版卸载器传了它不认识的 `/KEEPDIR`，旧卸载器按老逻辑删整个目录，而它安排的延迟 `rmdir` 又正好落在新安装器解压之后。**更关键的是流程错误：我当时直接拿真实数据做验证，没有先备份。** 后来靠「备份 → 校验 → 失败即中止」堵上，但那次确实丢了数据。

**② 一次判断升级（1.5.0）**
1.4.3 已经能用了，但复盘时想通：**「先卸载再装」这个方向本身是错的** —— 卸载器是为「删掉这个软件」设计的，不是为「换个版本」。于是推倒重来，代码反而少了 100 行。

**③ 一次误判（1.6.0）**
以为「82% 的作业缺截止时间」，去详情页补，补到 0 条 —— 因为那些都是**已交的**。真正的问题是状态判断错了：学习通列表每行有 `status` 属性（1=未做 / 2=过期 / 4=已批改），而「已批改」那行只显示分数、没有文案，之前靠文案判断，就把 16 条已交的当成了待办。

## 四、教训（写下来防复发）

1. **涉及删/覆盖用户数据的测试，必须先备份。** 1.4.x 那次就是拿真实数据做实验。
2. **「装不上」和「升级装不上」是两类问题。** 前者缺依赖，后者是进程占用，不能混着修。
3. **数据可以少，但不能假。** 拒绝用「发布时间 + 7 天」去编一个截止时间。
4. **静默比报错更坏。** 1.6.1 那三条（非法日期进位、空 body 崩溃、锚点日不同步）共性都是「不报错，但结果和用户以为的不一样」。
5. **用户报的现象 ≠ 根因。** 1.6.0 用户说「没截止时间」，根因是状态判断错；1.6.1 用户说「改日期跳回」，根因是合并对象时把旧锚点带进去了。
