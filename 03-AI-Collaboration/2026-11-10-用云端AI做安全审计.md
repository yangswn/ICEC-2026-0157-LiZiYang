## 一、我为什么要让 AI 来"挑毛病"

课铃这个程序**我自己用起来一直是正常的**：任务能同步、提醒能弹、日志有记录。做到第 11 版的时候，我甚至觉得它"差不多了"。

但有一个我一直没底的地方：**它开了一个本地 HTTP 服务**。也就是说这个程序除了给我看界面，还在 `127.0.0.1` 上监听着一个端口。这些东西**我自己平时根本不会去碰**，也就无从判断它安不安全。

我想到的办法是：**换一个角度，让 AI 不帮我写代码，只帮我在代码里找问题。**

这个用法跟我前面几版不一样 —— 前面都是"我说需求、它写实现"，这次是"**我给代码、它挑刺**"。这两种用法对 AI 的要求完全相反：写代码的 AI 倾向于配合我，审代码的 AI 才需要对抗我。

## 三、它报回来的东西：14 项缺陷

分级方式是 **P0（安全）/ P1（功能）/ P2（解析与错误码）/ P3（工程一致性）**。

**按分级统计，P0 占了 4 项，全都指向同一个地方：本地 HTTP 服务被外部网页滥用。**

### 已修（下表的状态码是我自己发请求验证的，不是 AI 说的）

| 缺陷 | 我的修法 | 我怎么验证 |
|---|---|---|
| 无 Host 校验，DNS rebinding 可读全量数据 | 只接受 `127.0.0.1:<端口>` / `localhost` / `[::1]` 三种 Host | 伪造 Host 头发请求 → **403** |
| 跨站 `text/plain` 写入（CSRF） | 写请求必须 `Content-Type: application/json` + `Sec-Fetch-Site` 同源 + `Origin` 校验 | 从别的页面发 POST → **403** |
| `/api/mistakes/inspect` 域名白名单可绕过 | 改成先用 URL 解析，再严格匹配 `chaoxing.com` 及其子域 | `evilchaoxing.com` → **400** |
| Cookie 可被跨站读取 | `sec-fetch-site: cross-site` 直接拒绝 | → **403** |
| 畸形 URL（如 `/%`）让请求永久挂起 | `decodeURIComponent` 加 try/catch + 静态兜底 | 立即返回，不再挂起 |
| 未捕获异常直接退出、日志丢失 | 先记录 → flush → 再退出 | — |

### 功能层修复（P1）

| 问题 | 修法 |
|---|---|
| 编辑任务会重弹所有提醒 | 只保留仍然有效的已发送键，不再"一改备注就全弹一遍" |
| 备份重复导入导致数据翻倍 | 按 `sourceKey` / 标题+时间去重，并恢复 `settings`；重复导入返回 `{"imported":0,"skipped":2}` |
| 静音时段输入 `99:99` 这类非法值 | 拒绝并保留原值，前端不再变空白 |
| 布尔设置把字符串 `"false"` 存成 `true` | 类型判断修正 |
| 测试弹窗失败时没有任何反馈 | 加 toast + `unhandledrejection` 全局兜底 |

### 解析与工程层（P2 / P3）

- 错题解析支持**未作答**和**整行复制粘贴的紧凑文本**
- 业务错误改为语义化状态码（404 / 422 / 409），不再一律 `SERVER_ERROR` 400
- 安装目录里带上 `tests/`，`npm test` 在安装副本里也能跑
- 环境变量新增 `CLASSBELL_*`，旧 `CAMPUSPULSE_*` 继续兼容
- 版本号统一由 `package.json` 驱动

### 我**没有**修的 3 项（这是我的判断，不是漏了）

| 项 | 为什么先不修 |
|---|---|
| 提醒队列上限 20、依赖宿主轮询 | 要改成 SSE 推送是结构性改动，**收益不确定**；只加了丢弃计数与日志，先看会不会真丢 |
| **Cookie 明文落盘**（只做了来源隔离，没做 DPAPI 加密） | 加密要动存取两端，**这是唯一我承认"技术上还没解决"的一项** —— 所以对外我只说"不上传"，不说"安全" |
| 端口冲突时没有握手失败提示 | 宿主已用随机空闲端口，冲突概率极低 |

## 四、这次协作里，哪些是 AI 做的、哪些是我做的

这一节是我特意写的，因为面试一定会问"这到底是不是你自己做的"。

| 环节 | 谁做的 |
|---|---|
| 找出 14 项缺陷、分级 | **AI**（它比我更熟悉这类攻击面） |
| 判断哪几项值得修、哪几项先放着 | **我**（AI 给的是清单，不是优先级决策） |
| 写具体修法 | 我提方向，AI 给实现，我改 |
| **验证修没修好** | **我** —— 伪造 Host、发跨站 POST、构造 `evilchaoxing.com`，看返回的状态码 |
| 决定"Cookie 明文"这条对外怎么表述 | **我** —— 只说"不上传"，不说"安全" |

**最关键的是最后两行。** AI 可以说"已修复"，但那只是一句话；**状态码 403 是我自己发请求打出来的**。

## 五、我从这次学到的

**① 本地程序不等于安全。**

我以前的想法是"我只监听 `127.0.0.1`，外面访问不到，所以没问题"。这次才知道：**只绑地址挡不住 DNS rebinding** —— 恶意页面可以把自己的域名解析到回环地址，再用一个外来的 `Host` 头访问这些接口。所以光绑地址不够，**还得校验 Host、校验来源**。

**② AI 的价值不只在"生成"，更在"审查"。**

我前面 11 版都是让 AI 帮我写。这次换成让它挑毛病，一次就翻出 4 个 P0。**同一个工具，换个用法，产出完全不同。**

**③ "AI 说修好了"不算数，得自己能验。**

后来我看那条 WebView2 的反馈也一样（见 `2026-11-10-WebView2-两次迭代.md`）：
功能返回"成功"和"真的成功"是两件事。**能复现的验证才算证据。**

## 六、这份记录和课程要求的关系

考核大纲里老师说过：**「一定要用 AI 协助完成，不用 AI 反而扣分」「要学会利用 AI、调整、完善，这个过程也是重要的」**。

我认为这次审计是这句话的一个具体例子：

- 不是"AI 帮我写了个功能"
- 而是"**我用 AI 找出我自己看不见的问题，然后我判断、我修、我验证**"

AI 是工具，判断是我的。
