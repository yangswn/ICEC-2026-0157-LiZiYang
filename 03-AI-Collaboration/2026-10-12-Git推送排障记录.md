## 二、逐个复盘

### 第 1 次：电脑上根本没装 Git

**我做了什么**：让 AI 检查了我的系统，发现 `C:\Program Files\Git` 不存在，

**我的体会**：我安装时一路点 Next 全默认，没有改任何选项。后来才知道这样是对的 ——

### 第 2 次：`command not found`（我花了最久的一个，也是最有价值的）

**我遇到的**：
```
$ git --version
bash: git: command not found
```

**为什么拖了 35 分钟**：我习惯用 **Ctrl+V** 粘贴命令。我原以为这个报错是
"Git 没装好"或者"窗口开错了"，于是一直在换窗口、找快捷方式，试了三四次都一样。

**真正的原因（我最后自己试出来的）**：**在 Git Bash 里，Ctrl+V 不是粘贴键。**

我后来换了个方式 —— 直接用手打，`git --version` 一次就通了。

**我后来搞清楚的事**：我去看了 Git Bash 的终端配置文件
（`C:\Program Files\Git\etc\minttyrc`），里面只有三行窗口尺寸设置，
**快捷键一个都没改过**，也就是说 **Ctrl+V 在这个终端里从来就不是粘贴键**。
它的粘贴键是 **`Shift + Insert`**。

我是从 Windows 其他软件里带来的习惯（Office、浏览器、微信都是 Ctrl+V），
这个习惯在终端里不成立。

**AI 在这里判断错了两次**：第一次它说"是你窗口开错了"，第二次又说
"是 Git Bash 的粘贴有 bug"。**两次都不对。** 真正的原因是我自己的按键习惯。
后来我想，如果它当时直接问一句"**你是怎么把命令弄进终端的？**"，
这个问题五分钟就能解决。

**我的体会**：
- 报错时，先想清楚"**我刚才具体做了什么操作**"，再怀疑环境
- **Ctrl+C 在终端里更危险** —— 它的含义是"立刻终止正在跑的命令"，不是复制。
  如果 `git push` 传到一半按了它，会直接把推送掐断

### 第 3 次：漏打空格

**我遇到的**：
```
$ git--version
bash: git--version: command not found
```

**原因**：`git` 和 `--version` 之间必须有一个空格。
没有空格，bash 会把 `git--version` 当成**一整个命令名**去找，当然找不到。

| 我写的 | 结果 | 为什么 |
|---|---|---|
| `git--version` | ❌ 找不到 | 被当成一个词 |
| `git --version` | ✅ 成功 | 两个词：命令 + 参数 |

**我的体会**：命令里的空格是**语法的一部分**，不是排版用的。
我后来养成一个习惯：AI 给我命令时，我会一个字符一个字符地看过去，
特别是空格的位置。

### 第 4 次：`fatal: not a git repository`

**我遇到的**：连着敲了 `git pull`、`git add`、`git commit`、`git push`，
**四条全都是同一个报错**：
```
fatal: not a git repository (or any of the parent directories): .git
```

**原因**：那天早上我新开了一个 Git Bash 窗口，**新窗口的起点是我的家目录**
（`C:\Users\24373`），不是我放项目的文件夹。所以 git 在那个位置找不到仓库。

**怎么看出来**：看提示符最后显示的路径 ——

| 提示符末尾 | 意思 |
|---|---|
| `UCRT64 ~` | 在家目录，**不是仓库** |
| `UCRT64 ~/Desktop/ICEC-2026-0157-LiZiYang` | 在项目里，**对了** |

**解决**：先 `cd` 回项目文件夹，再敲那些命令就好了。

**我的体会**：**每次新开窗口，第一件事是确认自己在哪**。
敲 `pwd` 或者瞄一眼提示符就行。

### 第 5 次：推送"成功"了，但数据表根本不在仓库里

这个是我遇到的最隐蔽的一个。

**我遇到的**：`git add .` → `git commit` → `git push` 三步都跑完了，
终端明明写着 `main -> main`，看起来一切正常。但数了一下提交的文件：

```
[main 4d9b616] 确定选题并建立数据表模板
 2 files changed, 171 insertions(+), 5 deletions(-)
 create mode 100644 01-Field-Discovery/采样与命名规范.md
```

**应该是 4 个文件，实际只有 2 个。两个 CSV 数据表凭空消失了。**

**原因**：`.gitignore` 里有一条规则：

```
01-Field-Discovery/raw_data/*
```

这条规则把 `raw_data/` 目录下的**所有文件**都排除了。
但考核明确要求"须包含本校实地采样原始数据表"，**这条规则屏蔽掉的恰恰是我必须交的东西**。
（这条规则是 AI 帮我写 `.gitignore` 时加的，它当时以为这个目录会装大体积原始数据。）

**为什么一直没被发现**：`git add .` 对忽略掉的文件**不报错、不提示**，直接静默跳过。
终端上一切正常，只有去数 `files changed` 的数量才会露馅。

**解决**：删掉那条目录级排除规则，改成按文件扩展名排除，然后重新提交：

```
git add .
git commit -m "修复 gitignore 并补传数据表模板"
git push
```

改完之后：
```
3 files changed, 45 insertions(+), 3 deletions(-)
 create mode 100644 01-Field-Discovery/raw_data/课题03-无线信号盲区-原始数据.csv
 create mode 100644 01-Field-Discovery/raw_data/课题06-噪声地图-原始数据.csv
```

**我的体会**：
1. **排除大文件要按扩展名（`*.mp4`），不要按目录（`raw_data/*`）** ——
   按目录排除很容易误伤必交内容
2. **`.gitignore` 的失败是静默的**，改完必须实测验证：
   ```
   git check-ignore -v <文件路径>
   git add -A --dry-run
   ```
3. **每次提交后数一下 `files changed` 的数量。** 数字和预期不符，就说明有东西被挡在外面了
4. **一个反直觉的发现**：出问题那次，`git add .` 的警告信息里**没有**出现 CSV 的文件名；
   修好之后，警告里**出现了**这两个文件名。
   → **警告信息有时候反而是"git 看得见这个文件"的证据**

### 第 6 次：网页上改了 README，本地却没变化

**我遇到的**：我在 GitHub 网页上编辑了 README，然后本地敲 `git status`，
发现本地完全不知道这件事。

**原因**：我在网页上那次编辑，**最后没点绿色的 `Commit changes` 按钮**，
所以改动根本没保存。

**我顺便搞明白的事**：GitHub 网页提交时那个弹窗有两个选项 ——

| 选项 | 什么意思 | 我该选哪个 |
|---|---|---|
| Commit directly to the `main` branch | 直接存进主分支 | ✅ 我一个人做项目，选这个 |
| Create a new branch... and start a pull request | 新建分支再提一个 PR | ❌ 这是给多人协作用的 |

**我的体会**：**在网页上改也行，但改完一定要点那个绿色按钮**。
另外，只要用过网页编辑，**本地再操作前要先 `git pull`**，
否则本地和远程会不同步，推送时会被拒绝。

## 四、这次我学到的知识点

1. **`warning` ≠ `error`**
   `git add .` 之后出现的那句 `LF will be replaced by CRLF` 是换行符格式提醒，
   Windows 上的正常现象，可以忽略。只有 `error` / `fatal` 才需要处理。

2. **空文件夹不会被 Git 上传**
   Git 天生不跟踪空目录。如果只建了文件夹不放文件，推上去之后 GitHub 上会是空的。
   解法是在每个空目录里放一个 `.gitkeep` 占位文件。
   我这次三个阶段目录里都放了，所以它们都正常显示在了仓库里。

3. **`Tab` 键能自动补全路径和文件名**
   输入前几个字母按 `Tab`，剩下的自动补齐，省打字还防拼错。

4. **终端和 Windows 软件的按键习惯不一样**
   `Ctrl+V` 不是粘贴（用 `Shift+Insert`），`Ctrl+C` 是"终止命令"而不是复制。
   这是我这次踩最久的坑，根源是我把别的软件的习惯带过来了。

5. **报错信息要完整看**
   报错的第一行往往就写明了原因。比如
   `bash: $'\E[200~git': command not found` 里，
   命令名前面那串乱码就直接暴露了"有隐藏字符被粘进来了"。

6. **`git push` 显示成功，不代表文件都在**
   要数 `git commit` 输出里的 `files changed` 数量。

## 六、以后我的日常流程

```
git pull                 # 先从云端拉最新（用过网页编辑就必须做）
git add .                # 把改动装箱
git commit -m "说明"     # 封箱存档
git push                 # 上传
```

**记住四个词：拉取 → 装箱 → 封箱 → 上传。**
